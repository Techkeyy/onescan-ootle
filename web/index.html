I

The four marks

For centuries, assay offices tested silver and punched four marks into it: who made it, that it meets the standard, who tested it, and when. OneScan punches the same four into a template's record, and each one stands for a check you can repeat.

Struck from live data: the marks of OneScan's own registry contract.

  1. I Maker's mark

    In silver: the initials of the workshop that made the piece.

    Here: the author key that published the template, with the repo and commit it claims. The initials and shield are derived from the key's bytes, so every author has exactly one mark and nobody can choose theirs.

  2. II Standard mark

    In silver: the metal meets a fineness, like 925.

    Here: an offline build of that commit is identical to the on-chain WASM, 32 of 32 sha256 bytes. The 32 is the fineness. A brass mark means the bytes match but the build raised warnings. A struck-through mark is a failed assay.

  3. III Office mark

    In silver: which assay office tested it.

    Here: an attestation in OneScan's SourceRegistry on Ootle mainnet, signed by the trusted verifier key. Your browser checks it against the live bytes before the mark is struck.

  4. IV Date letter

    In silver: the year of assay, as a letter that cycles.

    Here: the epoch the attestation was entered on chain. The letter is the epoch counted A to Z, and the shield changes with every cycle of 26 epochs.

II

Why bytes need hallmarks

Every call to a template signs against code you cannot read.

A wallet shows a function name and its arguments. The logic behind them is compiled WASM. A GitHub link in a README proves nothing on its own: it only counts if that exact commit rebuilds the exact bytes on chain. Silver had the same problem, which is why the hallmark exists.

Verified source is not an audit. A hallmark proves which public commit built the bytes. It does not mean the code is safe. Read the source.
